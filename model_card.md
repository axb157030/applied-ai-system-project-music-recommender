
## Limitations and Biases of the system

 I think some obvious biases and limitations are that the application is only reading from 50 songs with a really limited set of attributes and is making recommendations based only on content-based filtering rather than a hybrid that includes collaborative filtering.  It provides recommendations solely on the user's preference.  The feedback the user's give to the recommended songs is quite limited, it is just a number from 1 to 10. The application Retreival Augumented Generation is limited to answering questions regarding music attributes. The knowledge base and external data does not update in real time and so is not most up to date. The song attributes (energy, valence and so on) were estimated by hand, not measured from audio, and the catalog leans toward English-language Western pop, game and film music, so listeners of other styles get weaker matches. Ratings only move the numeric targets (energy, tempo, ...). They never change mood, genre or occasion, which carry most of the score, so the list can stay stuck on one mood. The retriever matches keywords, so a question worded with none of the docs' words finds nothing.
 Also when testing the application it was not that good at recommending based on user feedback. When I rate songs and ask it to regenerate, in addition to the reasons on why the new recommended songs are regenerated, I also want to listen to the music of those songs. Also more so it should also take feedback from the prompts I gave and it does not seem to do so well. Example: `I gave my ratings for them. But the previous recommended song sha la la by rainchy was the one I absolutly wanted. Now based on the feedback I gave recommend me some more songs. My preferences are sha la la by rainchy and look at the other ratings I gave`. This response of that prompt was `I didn't catch a preference in that. Try something like 'calm songs for studying'. Tell me more about what you like, ask me a question, or type 'refine', 'recommend', 'rate' or 'quit'.` It should extract data from that feedback from that prompt and well should be better at extracting user preferences. I wanted the Rainchy song to be at the forfront. It also does not appear to accumulate the ratings I gave for each song and use it to recommend songs the user may like more based on their history.

 ## Could your AI be misused and how can you prevent that.

 Yes it can be misued. I made guardrail.py to protect from them. The guardrail checks the user's text before Gemini sees it for prompt injection ("ignore all previous instructions"), personal data (emails, phone numbers, card numbers), self-harm (it answers with a caring message and a crisis line instead of a refusal) and very long input. I chose not to use a long list of bad words, because a word list cannot tell "I hate sad songs" from abuse and would block the opinions the interview needs. It is still limited: it is pattern matching, so a cleverly reworded injection could get through. Other protections are built into the design: Gemini's output is validated before use, and only songs in the catalog can ever be recommended. I would use Garak or PyRIT to test the guardrails or even better import and use guard roles such as `guardrails-ai`.

## Testing results and surprises (drafted from the real runs, please rewrite in your own words)

- **A rule that looked fine did not learn.** The unit tests for my first rating rule passed, but a simulated user whose taste was low energy went from an average rating of 2.8 to 2.2 to 2.8. When every song is rated low, "move away from the disliked songs" has no direction. Comparing each rating with the round's average fixed it (2.8, 3.4, 5.4). Passing unit tests did not mean the system worked.
- **A high match percentage is not satisfaction.** One song had a 96% match and was rated 2/10.
- **Gemini invented things when it had no docs.** Asked about explicit songs it described "[E] badges" and an "Explicit Content Filter" that do not exist. With the docs (RAG) it described the real behavior.
- **Gemini's output was valid-looking but wrong in small ways.** It returned the occasion "study or focus" (no song has that label), wrapped JSON in a code fence, and gave different numbers for the same comment on different runs. Validation in code catches all of these.
- **The same sentence worked or failed depending on retrieval.** "I like acoustic" returned nothing until the word-to-number tables were always included.
- **Comments were misread.** "too slow and sleepy" once made Gemini lower the energy target. Telling it whether the song was liked or disliked, and moving numbers only halfway, fixed it.
- **Evaluation:** 135 unit tests and 57 harness checks pass (`python eval/run_eval.py --live`). The harness uses fake users, so it shows the loop can learn a simple taste, not that real people will be satisfied.
